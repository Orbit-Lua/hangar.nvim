                                                 *hangar.txt* *hangar* *hangar.nvim*

Manage language servers, debug adapters, formatters, linters, Tree-sitter
parsers and Mason packages from one view.

This help lists the public interface. The guide in `doc/guide.md` of the
repository describes the view, statuses, locks and session behavior.

------------------------------------------------------------------------------
                                                                *hangar.close()*
                                `hangar.close`()

Close the open view. Running operations continue.

------------------------------------------------------------------------------
                                                                *hangar.setup()*
                            `hangar.setup`({{opts}})

Validate {opts} and fill the defaults. {opts} is optional. See
|hangar-options|.

Setup installs the integrations (|hangar-integrations|). A repeated call
replaces the options, drops cached state and failures, and closes the open
view. It raises an error while a toggle or an installation
runs.
Parameters ~
{opts} `(optional)` `(Hangar.Options)`

------------------------------------------------------------------------------
                                                               *hangar.filter()*
                      `hangar.filter`({category}, {by_ft})

Apply saved enablement and order to a table of tool names by filetype.
Use it for conform's `formatters_by_ft` and nvim-lint's `linters_by_ft`, so
intent from the view persists across restarts without an adapter.

Returns a new table. {by_ft} becomes the activation that re-enabling
restores. Unregistered names stay after the registered ones. Option keys,
function entries and the `*` and `_` keys stay unchanged.

Call it after |hangar.setup()|.
Parameters ~
{category} `(string)` `"formatter"` or `"linter"`
{by_ft} `(table<string, any>)` tool names by filetype
Return ~
`(table<string, any>)`
Usage ~
>lua
  opts = {
    formatters_by_ft = require("hangar").filter("formatter", {
      lua = { "stylua" },
    }),
  }
<
------------------------------------------------------------------------------
                                                            *hangar.update_ui()*
                          `hangar.update_ui`({values})

Replace the view options with {values}. A key that {values} omits takes
its default. An open view rebinds its keys and redraws. See |hangar-ui|.

It raises an error when `categories` is empty or names an unknown category.
Parameters ~
{values} `(table)`

------------------------------------------------------------------------------
                                                                 *hangar.open()*
                                `hangar.open`()

Open the view for the current buffer, or focus the open view.

------------------------------------------------------------------------------
                                                                 *hangar-events*

`User HangarChanged`
An open view redraws when this event fires. |hangar.update_ui()| fires it.
Fire it yourself after you change the `ui` table that you passed to
|hangar.setup()|.

------------------------------------------------------------------------------
                                                             *hangar-highlights*

Each status icon has its own group: `HangarIconEnabled`, `HangarIconIdle`,
`HangarIconInfo`, `HangarIconInstalling`, `HangarIconWarning`,
`HangarIconError`, `HangarIconUnknown` and `HangarIconDisabled`.

Category tabs use `HangarCategoryActive` and `HangarCategoryInactive`.

Each group links to a built-in group by default. To override a group,
define it in your color scheme or configuration.

                                                                *hangar-options*

Options of |hangar.setup()|. Every option is optional.
Class ~
{Hangar.Options}
Fields ~
{registry} `(optional)` `(Hangar.Registry)` install mapping and metadata (|hangar-registry|)
{defaults} `(optional)` `(fun(): { formatter?: table<string, string[]>, linter?: table<string, string[]> })` user default orders

{border} `(optional)` `(any)`

------------------------------------------------------------------------------
                                                           *hangar-integrations*

Backends that hangar gates from saved state. Each one defaults to `true`;
set it to `false` to leave that backend alone. Hangar applies the conform,
nvim-lint and nvim-dap integrations when the plugin loads, so hangar must be
set up before them.
Class ~
{Hangar.Integrations}
Fields ~
{lsp} `(optional)` `(boolean)` `vim.lsp.enable` and clients of disabled servers
{dap} `(optional)` `(boolean)` debug sessions of disabled adapters
{conform} `(optional)` `(boolean)` conform `formatters_by_ft`
{lint} `(optional)` `(boolean)` nvim-lint `linters_by_ft`
{treesitter} `(optional)` `(boolean)` Tree-sitter highlighting of disabled parsers

------------------------------------------------------------------------------
                                                               *hangar-adapters*

Owners that hangar calls for runtime changes.
Class ~
{Hangar.Adapters}
Fields ~
{linter} `(optional)` `({ logs?: fun(name: string): table[] })` run errors recorded for a linter

------------------------------------------------------------------------------
                                                                     *hangar-ui*

View options. |hangar.setup()| fills the keys that `ui` omits. Replace them
later with |hangar.update_ui()|.

- `categories`: category names in tab order; a nonempty list.
- `labels`: tab label by category.
- `mappings`: list of `{ keys, action, description }`.
- `width`, `height`, `details.width`: window sizes in cells.
- `layout`: `padding.vertical`, `padding.horizontal`, `column_gap`, `gap`
  and `margin` in cells.
- `missing_package_policy`: `"auto"` or `"manual"`.

------------------------------------------------------------------------------
                                                               *hangar-registry*

The registry is optional. It adds install mapping and metadata to the tools
that hangar discovers from the backends. Keys are logical tool names, by
category: `lsp`, `dap`, `linter`, `formatter`, `parser` and `package`.
`formatter_defaults` and `linter_defaults` set the default order by
filetype.

Annotate a registry table with `---@type Hangar.Registry`. |hangar.setup()|
rejects an unknown key, field or value with an error that names its path.
Class ~
{Hangar.Registry}
Fields ~
{lsp} `(optional)` `(table<string, Hangar.Definition>)`
{dap} `(optional)` `(table<string, Hangar.Definition>)`
{linter} `(optional)` `(table<string, Hangar.Definition>)`
{formatter} `(optional)` `(table<string, Hangar.Definition>)`
{parser} `(optional)` `(table<string, Hangar.Definition>)`
{package} `(optional)` `(table<string, Hangar.Definition>)`
{formatter_defaults} `(optional)` `(table<string, string[]>)` formatter order by filetype
{linter_defaults} `(optional)` `(table<string, string[]>)` linter order by filetype

------------------------------------------------------------------------------
                                                             *hangar-definition*

One registry entry.

- `ft`: filetypes that the tool supports.
- `mason`: Mason package that installs the tool.
- `runtime_name`: backend name, when it differs from the logical name.
- `note`: text that details show.
- `source`: who manages the tool (|Hangar.Source|).
- `plugin`: Lua module that starts this LSP client outside
  `vim.lsp.config`, such as `"typescript-tools"`.
Class ~
{Hangar.Definition}
Fields ~
{ft} `(optional)` `(string[])`
{mason} `(optional)` `(string)`
{runtime_name} `(optional)` `(string)`
{note} `(optional)` `(string)`
{source} `(optional)` `(Hangar.Source)`
{plugin} `(optional)` `(string)`
